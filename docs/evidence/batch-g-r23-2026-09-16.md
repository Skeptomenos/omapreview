# Batch G: R23 performance evidence

Date: 2026-09-16

Status: ready for integration

## Result

Batch G measured the requested R23 paths on generated text-layer and
image-only PDFs. The benchmark is model-level evidence. It does not claim
that PyMuPDF time is the same as GTK frame or input latency.

No production source changed. The reproducible tool is
[`scripts/bench_r23.py`](../../scripts/bench_r23.py).

The main finding is thumbnail refresh cost for scanned-style pages. The
12-page scanned fixture took 395.7 ms for two raster sizes per page. The
50-page scaling fixture took 1,650.8 ms. Text search remained below 22 ms on
12 pages and took 178.4 ms on 100 pages. The recorder model callback stayed
below 1.1 microseconds at p95.

## Model measurements

All times are wall-clock measurements from `perf_counter_ns`. Full-profile
values are medians over five repetitions. Scaling values have one sample, so
they are point measurements rather than stable percentiles.

| Probe | Full text, 12 pages | Full scanned, 12 pages |
| --- | ---: | ---: |
| Open PDF | 0.203 ms | 0.198 ms |
| Thumbnail refresh | 48.082 ms | 395.664 ms |
| Search: open plus scan | 21.775 ms | 0.608 ms |
| Search: scan only | 21.508 ms | 0.470 ms |
| Search hits | 108 | 0 |
| Six page-operation sequence | 332.674 ms | 13.720 ms |
| Eight-entry retained snapshot bytes | 3,414,194 B | 4,994,895 B |
| Tracemalloc peak | 3,902,322 B | 5,661,201 B |
| Recorder callback p95, 800 points | 0.917 us | 1.084 us |
| Recorder SVG serialization | 1.469 ms | 1.660 ms |
| CLI snapshot subprocess | 357.534 ms | 373.331 ms |

Thumbnail refresh includes two PyMuPDF rasterizations per page and PNG
encoding. It excludes `Gdk.Texture` construction and GTK layout. CLI
snapshot includes process startup and output publication.

The six page operations were rotate page 1, move the last page, crop page 1,
rotate page 2, move page 3 after page 1, and rotate the last page. The text
fixture's per-operation medians were 15.969, 31.813, 47.663, 63.305, 79.071,
and 94.850 ms in that order. The scanned fixture's values were 0.848, 1.410,
2.055, 2.582, 3.150, and 3.681 ms. `PagePreviewState.append_op` rebuilds the
scratch PDF after each operation. The scaling profile omits this sequence to
keep the large-document run bounded.

`GDK_BACKEND=x11` and `CUA_DRIVER_RS_ENABLE_WAYLAND` unset. It used only the
generated 12-page text fixture and an isolated signature directory.

- The editor opened with all 12 thumbnail rows visible.

## Surface applicability and recommendation

The CLI snapshot subprocess passed for both fixtures in both benchmark
profiles. A separate smoke run also passed page listing, snapshot generation,
and isolated signature listing. Its outputs are in
`/home/david/.local/state/omapreview/coordination/evidence/batch-g/20260916T060022Z-cli-smoke/`.
No CLI code changed. No MCP code or MCP surface changed, so MCP performance
was not claimed; the repository MCP tests remain the applicability check.

The next bounded performance item should target thumbnail refresh, with a
fresh baseline that includes `Gdk.Texture` creation and GTK layout. A useful
initial budget is 250 ms for the 12-page text fixture and 1,000 ms for a
50-page scanned fixture, measured on the same host. The follow-up should test
whether avoiding duplicate rasterization is sufficient before considering a
small cache or worker. This batch does not implement that change.

History also deserves a product decision. Eight saves retain 28.5 MB of exact
snapshot bytes for the 100-page text fixture. Any cap or compression policy
must define undo expectations before implementation.

No user PDFs were opened or inspected. The large scaling run does not measure
page-operation latency. The generated fixtures are intentionally simple, so
the measurements should guide the next probe rather than serve as a universal
PDF guarantee.
